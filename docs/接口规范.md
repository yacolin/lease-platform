# lease-platform 接口规范

> 版本：1.0 ｜ 适用范围：后端 `/api/v1/**` 全部接口 ｜ 关联：`db/README.md`（主键/表规范）、`README.md`（接口一览）

## 1. 总览

- 基础路径：`/api/v1`；HTTP 端口 8080（开发默认）。
- 数据格式：JSON（UTF-8）。
- 核心思想：**双轨模式** —— 同一个业务实体（如商品）对外提供「公开浏览」与「管理端管理」两套接口，路径用 `public` 前缀区分，**实现上也是两套独立的控制器与只读/CRUD 服务方法**，业务规则与权限天然隔离。
- 接口文档：springdoc 按端分组输出独立 OpenAPI JSON（见 §7），Swagger UI `http://localhost:8080/swagger-ui.html`。

## 2. 路径与端点约定

```
/api/v1
├── /public/**        对外浏览（白名单，无需登录，只读）
├── /auth/**          认证（白名单，双登录/刷新/登出）
├── /me               我的（需登录，当前用户资料）
└── /{resource}/**    管理端（仅 user_type=1 管理员 token，见 lease.security.admin-paths）
```

### 2.1 各段职责

| 前缀 | 权限 | 用途 | 是否写操作 |
|---|---|---|---|
| `/api/v1/public/**` | 白名单放行，无需登录 | 小程序/任意客户端的**只读浏览** | 否 |
| `/api/v1/auth/**` | 白名单放行 | 登录/刷新/登出（`login` 属管理端，`wx-login` 属小程序） | 是（仅认证令牌） |
| `/api/v1/me` | 需登录（任意类型） | 当前登录用户资料 | 部分（PUT） |
| `/api/v1/{resource}/**` | 仅管理员（user_type=1） | 管理端完整 CRUD | 是 |

> 认证方式：请求头 `Authorization: Bearer <accessToken>`；未携带/无效 token 访问受保护接口返回 403；业务侧未登录（如刷新失效）返回 401。

## 3. 双轨模式规范（对外浏览 vs 管理端）

同一业务实体若同时需要「对外浏览」与「管理端管理」，**必须**拆成两套接口，禁止共用同一方法再套权限。

### 3.1 路径与控制器

| | 对外浏览 | 管理端 |
|---|---|---|
| 路径 | `/api/v1/public/{resource}**` | `/api/v1/{resource}**` |
| 控制器 | `XxxPublicController` | `XxxAdminController` |
| 服务方法 | `publicList` / `publicPage` / `publicGet` / `publicList(date)` | `page` / `getById` / `create` / `update` / `delete` / `updateStatus` |
| 标签（@Tag） | `xxx（公开）` | `xxx（管理端）` |

### 3.2 业务规则（四个层面的区别）

1. **能力**：对外端**只读**；管理端完整 CRUD（含状态推进，如上下架 `PUT /{id}/status`）。
2. **数据可见性**：对外端**强制过滤**对外可见状态，管理端可查全部（可见性字段作为可选筛选条件）：
   - 商品：对外仅 `is_available=1`（上架）；详情当下架商品为 **404**（不泄露存在性）
   - 分类：对外仅 `status=1`（启用）
   - 菜单：对外仅 `is_available=1`（供应中）
3. **权限**：对外端进白名单（`whitelist`）；管理端进 `admin-paths`（仅 user_type=1）。
4. **限额**：对外分页 size 上限 100；管理端上限 1000。

### 3.3 参照实现

`prd` 域是双轨模式的样板：

| 实体 | 对外 | 管理端 |
|---|---|---|
| 分类 | `GET /api/v1/public/categories`（仅启用） | `/api/v1/categories` CRUD |
| 商品 | `GET /api/v1/public/products`、`/products/{id}`（仅上架，下架 404） | `/api/v1/products` CRUD + `PUT /products/{id}/status` |
| 菜单 | `GET /api/v1/public/menus?date=`（缺省今天，仅供应中） | `/api/v1/menus` CRUD |

## 4. 认证与权限分层

### 4.1 双登录（双 token）

| 端 | 接口 | 凭据 | 签发 user_type |
|---|---|---|---|
| 管理端 | `POST /api/v1/auth/login` | `{username, password}`（bcrypt 校验 `usr_admins`） | 1（ROLE_ADMIN） |
| 小程序 | `POST /api/v1/auth/wx-login` | `{code}`（开发 mock 固定复用 `mock_dev_user`） | 2/3 |

- `POST /api/v1/auth/refresh`：refresh token 轮换续期（存 Redis `auth:refresh:{userType}:{userId}`，复合身份防串号）。
- `POST /api/v1/auth/logout`：作废 refresh token（管理端/小程序共用）。
- access token 短时效（2h），refresh token 7 天。

### 4.2 三层权限模型（`application.yml` `lease.security`）

| 层 | 配置 | 放行条件 |
|---|---|---|
| 白名单 | `whitelist` | 无需认证（`/api/v1/public/**`、`/api/v1/auth/**`、Swagger、健康检查） |
| 管理端 | `admin-paths` | 仅 `user_type=1` 管理员 token（映射 `ROLE_ADMIN`） |
| 其余 | — | 任意已登录用户（如 `/api/v1/me`） |

> **新增管理端接口时必须**把路径补入 `lease.security.admin-paths`，否则默认只要求"登录"而非"管理员"。

## 5. 统一响应与错误码

### 5.1 响应信封

```json
{ "code": 0, "message": "成功", "data": { } }
```

- `code=0` 成功；非 0 见错误码表。
- 成功时携带 `data`；`data` 为 null 时（如 DELETE）整体省略（jackson `non_null`）。

### 5.2 分页

```json
{ "code": 0, "data": { "total": 8, "list": [ ] } }
```

查询参数统一 `page`（默认 1，最小 1）、`size`（默认 10，对外 ≤ 100、管理端 ≤ 1000）。

### 5.3 错误码（HTTP 状态与业务码解耦）

| 业务码 | 含义 | HTTP |
|---|---|---|
| 0 | 成功 | 200 |
| 40000 | 参数错误（含校验失败，返回字段级明细 `{field, message}`） | 422 |
| 40100 | 未登录 / 令牌无效或过期 | 401 |
| 40400 | 资源不存在 | 404 |
| 40900 | 状态冲突 / 存在依赖不允许操作 | 409 |
| 50000 | 服务器内部错误（对外不暴露细节） | 500 |

## 6. 数据格式约定

- **时间**：统一返回 epoch 毫秒数字（`TimeUtil.toEpochMillis`）；日期字段（如 `menu_date`）返回 `yyyy-MM-dd` 字符串；请求时间参数用 `@DateTimeFormat(iso = ISO.DATE)`。
- **金额**：整数 `Long`（数据库 `BIGINT`），**最小单位为「分」**；全链路（DB / 接口出入参 / 微信支付）统一以分为单位，杜绝浮点/小数精度问题（前端同样传分，如 12 元 = 1200）。折扣率（`discount_rate` / `equivalent_discount`）、时长（`duration_hours` / 免费时长）等非金额小数保持 `DECIMAL`。
- **规格等结构化信息**：数据库 JSON 存储，对外返回时解析为对象。
- **命名**：请求 DTO 用 `XxxCreateReq` / `XxxUpdateReq` / `XxxStatusReq`；响应用 `XxxVO`；字段驼峰（`map-underscore-to-camel-case` 已全局开启）。
- **主键**：业务表雪花 ID（`IdType.ASSIGN_ID`），配置表自增；详见 `db/README.md`。

## 7. 接口文档分组与前端请求文件生成

springdoc 按端输出独立 OpenAPI JSON（`/v3/api-docs/{group}`，Security 白名单已放行）：

| 组 | 覆盖接口 | OpenAPI JSON |
|---|---|---|
| `admin`（管理端） | 管理员登录/登出 + 管理端 CRUD | `/v3/api-docs/admin` |
| `public`（公开/小程序端） | 公开浏览 + 微信登录/刷新/登出 + 我的 | `/v3/api-docs/public` |

- 分组配置：`application.yml` → `springdoc.group-configs`（`group` 为 URL 后缀，`display-name` 为 UI 显示名）。
- Swagger UI 顶部只保留「管理端 / 公开·小程序端」两个切换。
- **前端请求文件生成**：按组拉取 JSON → 按模块拆分为 `api/*.js`（模块/文件名 = 英文 tag name，如 `api/admin/roomAdmin.js`；每个文件顶部注明后端契约，如 `// 后端契约：POST /api/v1/auth/wx-login`）→ 配合统一封装 `utils/request.js`（BASE_URL + token 注入 + 401 自动重新登录 + 统一响应解包）。
- **operationId 约定（强约束）**：**每个 `@Operation` 必须显式声明 `operationId`**（英文驼峰，如
  `getMeetingReservation` / `createCoupon` / `listMyCoupons`）。前端按 operationId 生成请求方法名
  （函数名）与前端注释锚点：缺省时工具会按路径推导（如 `getApiV1MeOrders`，不专业且随路径变化不稳定），
  中文会变成拼音（如 `huodeyuyue`）。operationId 一经发布不可随意改名（前端文件已依赖）；
  同一 tag 下必须唯一。

## 8. 交易域补充约定（1.2 交易可靠性与订单闭环）

1.2 新增「支付单 / 退款单 / 订单状态历史 / 幂等记录」四张表与查询接口（roadmap 1.2），
资金链路可完整追踪。端点一览：

| 端 | 方法 | 路径 | 说明 |
|---|---|---|---|
| 我的 | GET | `/api/v1/me/payments` | 我的支付单分页（`bizType`：1-充值, 2-咖啡订单, 3-正餐预订, 4-会员购买） |
| 我的 | GET | `/api/v1/me/refunds` | 我的退款单分页 |
| 我的 | GET | `/api/v1/me/status-history?bizType=&bizId=` | 我的订单状态历史（服务层校验归属） |
| 管理端 | GET | `/api/v1/payments` | 支付单分页（paymentNo/bizType/status 筛选，已注册 `admin-paths`） |
| 管理端 | GET | `/api/v1/refunds` | 退款单分页（refundNo/status 筛选，已注册 `admin-paths`） |
| 管理端 | GET | `/api/v1/status-history?bizType=&bizId=` | 订单状态历史（已注册 `admin-paths`） |

约定：

1. **支付事实与业务事实分离**：业务域（充值记录/订单/预订/购买记录）只保存业务状态；
   `trd_payments` 统一保存支付事实（`biz_type` + `biz_id` 关联业务单），退款必须挂在支付单下。
2. **支付幂等**：支付成功用 `status 0→1` 条件乐观更新；微信回调外层用 `sys_idempotency`
   （key 如 `WX_NOTIFY:{out_trade_no}`，请求体 SHA-256 防重放）去重，重复通知不重复入账。
3. **退款幂等**：`trd_refunds.idempotency_key` 唯一（如 `ORDER_CANCEL_REFUND:{orderId}`），
   同一业务场景重复执行只产生一笔退款；退款总额不允许超过支付金额（服务层校验）。
4. **状态历史**：咖啡订单/正餐预订每次状态变更写入 `ord_order_status_history`
   （`from_status`/`to_status`/`operator_id`/`operator_type`/`reason`），初始状态 `from_status=NULL`。
5. **新增资金类接口**：同样遵循「管理端路径进 `admin-paths`、我的进 `/api/v1/me/**`、
   `@Tag` 英文驼峰、`@Operation` 描述」约定；写操作必须落在业务域（如取消/商家退款），
   支付单/退款单仅提供查询接口，不允许绕过业务状态直接改资金事实。

## 9. 商品域补充约定（1.3 商品中心 SKU 化）

1.3 将 `prd_products` 收拢为 **SPU**，价格/库存下沉到 `prd_skus`，规格结构由
`prd_spec_groups` / `prd_spec_values` 承接。端点一览（管理端，均已在 `admin-paths` / admin 文档组）：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET/POST | `/api/v1/products/{id}/skus` | SKU 列表 / 创建（`specValueIds` 为空 → 默认 SKU，无规格） |
| PUT/DELETE | `/api/v1/products/{id}/skus/{skuId}` | 更新 / 删除（被订单明细引用时 409） |
| PUT | `/api/v1/products/{id}/skus/{skuId}/status` | SKU 上下架（0-停售, 1-可售） |
| GET/POST | `/api/v1/products/{id}/spec-groups` | 规格组列表（含规格值）/ 创建（可携带 values） |
| PUT/DELETE | `/api/v1/products/{id}/spec-groups/{groupId}` | 更新（values 全量替换）/ 删除（连同规格值） |
| PUT | `/api/v1/products/{id}/status` | 商品状态生命周期：0-草稿, 1-待审核, 2-上架, 3-下架, 4-停售（与 is_available 联动） |

约定：

1. **SPU/SKU 模型**：商品创建时自动生成默认 SKU（价格=SPU 价）；规格商品用「规格组/规格值」
   描述维度，SKU = 各规格值的笛卡尔积，`spec_value_ids`（值 ID 组合）与
   `spec_snapshot`（`{组名: 值名}` 快照）落库；SKU 售价/库存独立维护。
2. **快照原则**：SKU 规格组合与价格以快照写入 `ord_order_items`
   （`sku_id` / `sku_name_snapshot` / `sku_price_snapshot` / `specification_snapshot`），
   商品与 SKU 后续变更不影响历史订单。
3. **引用保护**：规格组被 SKU 引用后禁止更新/删除（保证 SKU 快照一致）；SKU 被订单明细
   引用后禁止删除（订单保留快照）。
4. **下单解析**：`POST /api/v1/me/orders` 明细可带 `skuId`（必须属于该商品且可售，否则 400）；
   缺省自动取该商品默认 SKU（首个可售），无 SKU 时回落 SPU 价格（1.0 兼容）。
5. **可见性**：公开端仅展示「上架」（product_status=2）商品与「可售」（status=1）SKU；
   商品状态与 1.0 `is_available` 联动（上架=1，其余=0）。

## 10. 会议室域补充约定（1.4 会议室资源化）

1.4 引入 **Room（mtg_rooms）→ Booking（mtg_bookings 占用表）→ Reservation（mtg_reservations 业务事实）**
三层资源模型。端点变化：

| 端 | 方法 | 路径 | 说明 |
|---|---|---|---|
| 我的 | PUT | `/api/v1/me/meeting-reservations/{id}/reschedule` | 改期（仅待确认/免费已确认可改；付费已确认需先取消重新预约） |
| 管理端 | PUT | `/api/v1/meeting-reservations/{id}/status` | 状态推进：已确认→使用中→已完成（body `{orderStatus:2|3}`，替换 1.0 的 `/complete`） |

约定：

1. **资源占用（Booking）**：每次预约创建一条 `mtg_bookings` 占用记录（`start_at`/`end_at` 为
   DATETIME），取消/完成/过期置「已释放」；时间冲突校验查占用表重叠（
   `start_at < 新结束 AND end_at > 新开始`），同会议室预约先对 `mtg_rooms` 行加锁
   （`SELECT ... FOR UPDATE`）串行化并发请求——保证 A 10:00-12:00 与 B 11:00-13:00 不能同时成功。
2. **预约订单化（1.4.5）**：付费预约关联 `ord_orders`（`order_type=4` 会议室）与
   `trd_payments`（`biz_type=5` 会议室订单）：创建时生成订单+支付单（不扣款），
   `pay()` 时余额扣款 + 支付单结算（乐观锁防并发重复支付）；取消/过期走 1.2 退款单/订单取消。
   免费预约无交易（不生成订单），直接已确认。
3. **生命周期**：`mtg_reservations.status`：0-待确认, 1-已确认, 2-使用中, 3-已完成,
   4-已取消, 5-已过期。免费时长「已用」统计口径：已确认/使用中/已完成。
4. **改期规则**：待确认（未支付）改期重算费用并同步订单应付与支付单金额；已确认且免费
   可改（改后超时付费则拒绝）；已确认且付费不支持改期（差额处理留 2.0 Payment Center）。
5. **惰性过期**：查询时把已过预约日且仍待确认/已确认的预约置为已过期（不退款），
   释放占用并取消关联订单；过期记录在查询接口触发（与 1.0 一致）。

## 11. 交易域补充约定（1.5 账户 / 钱包）

1.5 将余额从 `usr_users` 剥离到 **acct_accounts 账户表**（余额唯一事实源）：

| 项 | 说明 |
|---|---|
| 账户 | `acct_accounts`（账户 ID = 用户 ID，1:1）：`available_balance` 可用 / `gift_balance` 赠送 / `frozen_balance` 冻结 |
| 账本 | `trd_balance_transactions` = 历史事实（新增 `frozen_balance_before/after`）；`transaction_type` 增 6-冻结, 7-解冻 |
| 服务 | `AccountService`（替代 1.0 的 BalanceService）：所有余额变动统一走它，行锁（`acct_accounts SELECT ... FOR UPDATE`）串行化同账户并发 |
| 资料 | `GET /api/v1/me` 的 `balance`/`giftBalance` 来自账户，新增 `frozenBalance` |

约定：

1. **账户 = 当前状态，流水 = 历史事实**：任何余额变动必须同时更新账户与写流水（同一事务），
   禁止绕过 AccountService 直接改 `acct_accounts`。
2. **消费策略（1.5.5）**：赠送余额优先扣，不足扣可用余额（混合扣款）；充值/赠送资金来源
   已区分，活动/退款余额按需引入（不过度拆分）。
3. **冻结/解冻（1.5.3）**：押金/预授权/待结算/退款处理中走 `freeze`/`unfreeze`（可用 ↔ 冻结），
   流水 `amount` 记可用余额变动（冻结为负、解冻为正），`frozen_balance_before/after` 记冻结变动。
   当前接入场景：会议室付费预约创建时预授权冻结，支付解冻后扣款，取消/过期解冻。
4. **存量数据**：V9 迁移把 `usr_users.balance/gift_balance` 回填到 `acct_accounts` 后删除列；
   新注册用户账户懒创建（首次余额操作/资料查询时建 0 余额账户）。

## 12. 营销域补充约定（1.6 运营 / 营销）

端点一览：

| 端 | 方法 | 路径 | 说明 |
|---|---|---|---|
| 管理端 | POST/GET/PUT/DELETE | `/api/v1/coupons[/{id}]` | 券模板 CRUD（满减/折扣；可指定业务/商品/分类；已被领取不可删，可停用） |
| 公开 | GET | `/api/v1/public/coupons` | 可领取优惠券列表（白名单，无需登录） |
| 我的 | POST | `/api/v1/me/coupons/{id}/claim` | 领取（重复领取 409；有效期 = 领取 + validity_days） |
| 我的 | GET | `/api/v1/me/coupons` | 我的优惠券（状态：0-未使用, 1-已使用, 2-已过期；惰性过期） |
| 下单 | — | `POST /api/v1/me/orders` / `me/meal-reservations` | 请求体可带 `couponId` 使用优惠券 |

约定：

1. **规则与快照分离（1.6.2）**：券规则存 `mkt_coupons`；领取时快照进 `mkt_user_coupons`
   （名称/类型/金额/折扣率/门槛/范围），下单时快照进订单（`coupon_id` / `coupon_name_snapshot` /
   `coupon_discount`）——规则可改，历史用户券与订单不受影响。
2. **折扣叠加链（1.6.4 基础）**：应付 = 原价 × 会员折扣率 × 充值折扣率 − 优惠券；
   满减券抵扣 min(满减金额, 折后金额)，折扣券抵扣 折后金额 × (1 − 折扣率)；
   门槛与指定商品/分类按折后订单校验。完整规则引擎（活动价/赠送）留 2.0。
3. **使用原子性**：下单事务内校验（apply）→ 落订单快照 → 标记用户券已使用（status 0→1 乐观更新 +
   绑定订单）；并发重复使用仅一次成功，失败整体回滚。
4. **会员权益（1.6.3）**：免费会议室时长 / 商品折扣 / 会议室等级价格 / 充值赠送在 1.0~1.4 已落地，
   本版与优惠券叠加联动验证，不重复造轮子。

## 13. 新增接口流程（新域套用清单）

以新业务域（如会议室 `mtg`）为例：

1. **建控制器**：需要对外浏览 → `MtgPublicController`（`/api/v1/public/rooms/**`，只读 + 强制过滤可见状态）；需要管理端 → `MtgAdminController`（`/api/v1/rooms/**`，完整 CRUD）。共用逻辑可下沉 service，但对外/管理端方法必须分离（`publicXxx` vs CRUD）。
2. **注册权限**：对外路径加入 `whitelist`；管理端路径加入 `admin-paths`。
3. **打标签 + operationId**：`@Tag(name = "roomPublic", description = "会议室浏览（公开）：无需认证，面向小程序端")`。**name 必须用英文驼峰**（前端按标签名生成请求文件，中文名会被工具转成拼音文件名，如 `huiyishigongkai`，不专业）；中文标签写进 `description`（Swagger UI 标签下方可见）。**每个 `@Operation` 必须携带 `operationId`（英文驼峰，如 `getMeetingReservation`）**：前端按 operationId 生成请求方法名/文件名，缺省自动推导或中文拼音都不专业且不稳定；同一 tag 内唯一、发布后不改名（详见 §7 operationId 约定）。
4. **登记文档组**：如管理端路径进入 `admin` 组、对外进入 `public` 组（按需调整 `paths-to-match`）。
5. **校验**：`mvn test` 全绿；对照 `make db-reset` 后的种子数据冒烟（白名单可匿名访问、admin token 可访问管理端、小程序 token 403）。
