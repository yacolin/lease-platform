# lease-platform 查询效率评估与多级缓存 / 布隆过滤器落地方案

> 评估范围：`src/main/java/com/example/leaseplatform` 全部 **125 个 HTTP 接口**（58 个 GET / 67 个写接口）、7 个业务域、31 张表。
> 参考实现：`gf-eshop/internal/logic/brands/cache.go`、`products/cache.go`、`products/repo_products.go`（Go + gogf）。
> 证据来源：源码逐行通读、`EXPLAIN` 实测（本机 MySQL 8 / `lease_db`）、`redis-cli` 运行时 keyspace 取证。
> 说明：本机为 seed 数据（`prd_products` 27 行、`ord_orders` 11 行），`EXPLAIN` 的 `rows` 估值无参考意义，**判断依据是 access type 是 `Table scan` 还是 `Index lookup`** —— 它决定数据量增长后是否退化。

---

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| Redis 是否被业务使用？ | **完全没有**。全仓唯一注入点是 `AuthService`，只存 refresh token 会话 |
| 是否有任何缓存注解？ | 全仓 **0 处** `@Cacheable` / `@CacheEvict` / `@CachePut` / `@EnableCaching` |
| 引入了 Redis 却没用的旁证 | 幂等表用的是 MySQL `sys_idempotency`，不是 Redis |
| 最严重的性能问题 | **不是缓存缺失，而是 `GET /me/meeting-reservations` 与 `GET /meeting-reservations` 在 GET 里做写操作 + N+1 循环**（见 §2.0） |
| 索引现状 | 10 个 Flyway 迁移脚本中 **没有任何一条 `ADD INDEX` / `CREATE INDEX`**，索引自建表后未演进 |
| 最该做缓存的接口 | 8 个 `/api/v1/public/**` 匿名只读接口 + 1 个订单统计接口 |
| 布隆过滤器真正值得上的接口 | **只有 1 条链路：商品详情**（`GET /public/products/{id}`） |

> **最重要的两条判断**
> 1. **缓存不是第一优先级。** 先修索引、无界查询、GET 里的写操作，收益远大于加缓存，且零风险。
> 2. **多级缓存与布隆过滤器是两件事，不要捆绑落地。** 小表（分类/会议室/充值档位/会员等级/优惠券）的收益全部来自 **L1 本地整表缓存**，布隆在那里是负收益；布隆只在"按 ID 点查 + ID 空间稀疏 + 存在探测流量"时才有效，本项目只有商品详情满足。

## 2. 查询效率评估

### 2.0 🔴 最严重：GET 接口里藏写操作 + N+1 循环

**`GET /api/v1/me/meeting-reservations`**（`MeMeetingReservationController.java:64`）与 **`GET /api/v1/meeting-reservations`**（`MeetingReservationAdminController.java:37`）在返回列表前会先执行惰性过期清理 `expirePastReservations()`（`MeetingReservationService.java:573-603`）：

```java
List<MtgReservation> expired = reservationMapper.selectList(new LambdaQueryWrapper<MtgReservation>()
        .lt(MtgReservation::getReservationDate, LocalDate.now())   // ⚠️ 无日期下限
        .in(MtgReservation::getStatus, List.of(STATUS_PENDING, STATUS_CONFIRMED)));  // ⚠️ 无 LIMIT
```

设 `E` = 过期行数、`Ep` = 其中"待确认且有费用"的行数，则该 GET 的 SQL 次数为：

```
E = 0 ：4 次
E > 0 ：5 + 3E + 3Ep 次
```

展开（`MeetingReservationService.java:573-603`）：

| 语句 | 次数 | 位置 |
|---|---|---|
| `selectList` 扫全部历史过期预约 | 1 | :574 |
| 批量 `UPDATE ... status IN (ids)` | 1 | :581 |
| `releaseBooking` 释放占用 —— **Java `for` 循环内** | **E** | :584-586 |
| 订单取消 update + 状态历史 insert | **2E** | :593-600 |
| `accountService.unfreeze`（行锁 + 更新 + 流水 insert） | **3Ep** | :590 |
| `selectPage` 列表（COUNT + LIMIT） | 2 | :354 / :339 |
| `selectBatchIds` 房间 | 1 | :647 |

**四重问题叠加**：

1. **GET 语义被破坏**：一个读接口在写库，且**没有任何事务包裹**——批量状态更新、每个 `releaseBooking`、每个 `unfreeze` 各自独立提交。循环中途崩溃会留下"预约已过期但占用未释放 / 余额仍冻结"的不一致状态。
2. **无界**：`reservation_date < CURDATE()` **没有日期下限**，`status IN (0,1)` 也没被清理过——历史越久，这个查询返回的行越多，最终**每次刷新列表都要扫全表历史**。
3. **N+1 放大**：`E` 行 → `3E + 3Ep` 条语句。`E` 到 1000 就是 3000+ 条 SQL。
4. **缓存会掩盖问题**：这两个接口**不能简单加缓存**——一旦命中缓存就跳过清理，过期逻辑失效。

> **正确修法**：把过期清理移到 `@Scheduled` 定时任务（如每 5 分钟），并用 `UPDATE ... WHERE reservation_date < ? AND status IN (...) LIMIT 1000` 分批推进；列表接口只做纯读。这**不是缓存问题，是架构问题**。

**✅ 已实施**（`MeetingReservationExpiryJob` + `MeetingReservationService.expirePastReservationsOnce`，见 commit `perf(mtg)`）。
实施中通过实测修正了上面两处初判，记录于此以免后人重蹈：

1. **不需要「日期下限」，但需要「不自带排序」。** 处理过的记录状态变为 `EXPIRED` 后
   自动退出 `status IN (0,1)` 过滤，因此反复调用天然自排空，日期下限非必需。
   真正关键的是**批查询不能带 `ORDER BY`** —— 实测（30 万行历史，`EXPLAIN ANALYZE`）：

   | 批查询形态 | 积压 10 万 | **稳态（积压≈0，即常态）** |
   |---|---|---|
   | **`LIMIT 500`（无 ORDER BY）** | 2.97 ms（走 `idx_status`，读满 500 即停） | **0.031 ms（走 `idx_status_date`，读 0 行）** ✅ |
   | `ORDER BY id LIMIT 500` | 2.05 ms | ❌ **167 ms，主键全表扫 30 万行** |
   | `ORDER BY reservation_date LIMIT 500` | 4.3 ms | ❌ 632 ms |

   原因：带 `ORDER BY` 时优化器为了「定序后取前 N 条」必须扫完全部候选行，
   稳态下无匹配行 → 退化成全表扫描。而每 5 分钟执行一次的全表扫描，
   比原来的惰性清理更糟。**无排序时优化器用 `idx_status_date` 范围扫描，取满 LIMIT 即停。**
   批选哪些行不影响正确性（本批处理完即退出过滤），故刻意不加排序。

2. **单批必须包事务。** 原实现「先批量置过期 → 再逐条释放占用/解冻/取消订单」，
   中途失败会留下「预约已过期但占用未释放 / 余额仍冻结」。现在整批在一个事务内完成。

3. **端到端验证**：启动应用 → 插入一条昨天日期的「已确认」预约 → 定时任务在第 60 秒
   准时触发并处理 1 条 → 状态 `1 → 5`。

**同类问题（较轻）**：`GET /api/v1/me/coupons`（`MktUserCouponService.java:80`）先执行 `expireUnused` 的 `UPDATE`（**无 `@Transactional`，autocommit 写**），再 `selectPage`。

#### 2.1.1 公开只读接口（热路径，匿名可刷量）

### 2.2 重复查询：一次请求内同一行查 2~3 次

这是**缓存收益最直接的证据**——不是"避免重复请求"，而是"避免同一次请求内的重复 SQL"。

`POST /api/v1/me/meeting-reservations`（创建会议预约）在同一事务内重复查询同一行：

| 重复对象 | 次数 | 位置 |
|---|---|---|
| `mtg_rooms` | **2 次**（先 `selectById`，随后 `lockRoom` 又 `FOR UPDATE` 查一次） | `:107` 与 `:109` → `:417` |
| `usr_enterprises` | **2 次**（`monthlyFreeHours` 与 `resolveOvertimeFee` 各调一次 `effectiveLevelCode`） | `:529`（经 `:517` 与 `:552`） |
| `usr_member_levels` | **2 次**（无房间覆盖价时，`:546` 被调用两次） | `:546`、`:563` |

该接口总 SQL 次数：

| 场景 | SQL 次数 |
|---|---|
| 个人用户 + 免费 | **7** |
| 个人用户 + 付费 | **14** |
| 企业会员（有覆盖价）+ 免费 | **11** |
| 企业会员（有覆盖价）+ 付费 | **18** |

`usr_member_levels` 与 `usr_enterprises` 是**计费规则类参照数据**（全表 3 行 / 2 行），做成 L1 常驻几乎零成本，却能直接消掉上面 2~4 条 SQL。这是 §4 中 A 级缓存的核心理由。

**✅ 已修复**（commit `perf(mtg)`）。修法不是加缓存，而是**同请求内只解析一次**：

- 新增 `MembershipContext` 记录 + `resolveMembership(user)`，一次解析出
  `levelCode` / `level` / `fallbackLevel`，供 `monthlyFreeHours` 与 `resolveOvertimeFee` 共用；
- `lockRoom()` 改为**返回锁定到的行**，`create` 直接用它做「可预约」校验，
  消除多余的 `selectById`（`requireBookableRoom` 已删除）。

| 重复对象 | 修复前 | 修复后 |
|---|---|---|
| `mtg_rooms` | 2 次（`selectById` + 行锁 `selectOne`） | **1 次**（行锁 `selectOne`，其返回值直接用于校验） |
| `usr_enterprises` | 2 次 | **1 次** |
| `usr_member_levels` | 2 次 | **1 次** |

### 2.8 📊 索引收益实测（50k/200k/100k/300k 行数据集，`EXPLAIN ANALYZE`）

为验证上述结论，在独立库 `lease_perf` 中灌入真实量级数据（`prd_products` 5 万、`ord_orders` 20 万、`mtg_reservations` 10 万、`sys_notifications` 30 万），用 `EXPLAIN ANALYZE` 取**实际执行时间**，加索引前后对比：

| 查询 | 加索引前 | 加索引后 | 提速 |
|---|---|---|---|
| **Q1** `publicPage` 无筛选 | **Table scan 50000 行** + filesort，**57.4 ms** | `Index lookup idx_avail_status_sort`，读 20 行，**0.061 ms** | **≈ 940×** |
| **Q2** `publicPage` 按分类 | `idx_category_id` 回表 12500 行 + filesort，15 ms | `Index range scan idx_cat_avail_sort`，读 62 行，**0.11 ms** | **≈ 136×** |
| **Q3** `orders/stats` 今日 | **Table scan 200000 行**，**52 ms** | `Index range scan idx_created`，读 547 行，**1.52 ms** | **≈ 34×** |
| **Q4** `GET /orders` 日期筛选 | `PRIMARY (reverse)` 扫 1074 行，0.88 ms | 未变（0.98 ms） | — 已足够好 |
| **Q5** `GET /me/orders` | `idx_user_id (reverse)`，0.07 ms | 未变 | — 已足够好 |
| **Q6** `unread-count` | `idx_user_id` + 事后过滤，0.13 ms | **`Covering index lookup idx_user_read_id`**，**0.0046 ms** | **≈ 28×** |
| **Q7** 通知列表 | `idx_user_id` + 事后过滤，0.125 ms | `Index lookup idx_user_read_id (reverse)`，**0.0034 ms** | **≈ 37×** |
| **Q8** 过期清理（无界） | **Table scan 100000 行**，匹配 33250 行，**54.2 ms** | ⚠️ **仍是 Table scan，52.4 ms —— 无改善！** | **见下** |
| **Q9** 免费时长聚合 | `idx_reservation_date` 范围扫描 | `idx_status_date` 范围扫描，4.08 ms | 见下 |

**两个必须诚实说明的反直觉结论：**

**① Q8：加索引救不了无界的过期清理。**
`reservation_date < CURDATE() AND status IN (0,1)` 命中了约 1/3 的表（33250/100000 行）。选择性太差，优化器判定**全表扫描比走索引更便宜**，因此新加的 `idx_status_date` 被直接忽略——**加索引后 52.4 ms，几乎无变化**。

必须**索引与有界化同时做**才有效。实测加上日期下限与 `LIMIT` 后：

```sql
-- 加日期下限 + LIMIT 1000 后，才真正用上索引
SELECT id FROM mtg_reservations
WHERE status IN (0,1) AND reservation_date < CURDATE()
  AND reservation_date >= CURDATE() - INTERVAL 60 DAY
ORDER BY reservation_date LIMIT 1000;
-- → Covering index range scan on idx_status_date，读 5000 行，10.2 ms（54.2ms → 10.2ms）
```

> 这从实证上印证了 §2.0 的结论：**过期清理必须改成"定时任务 + 分批 + 日期下限"，单靠加索引无效。**

**② Q9：附录 A 中我原拟的 `idx_ent_date_free_status` 组合索引未被优化器采用。**
实测该查询优化器选择 `idx_status_date`（读 3750 行，**4.08 ms**）；强制 `FORCE INDEX(idx_ent_date_free_status)` 反而更慢（读 7416 行，**11.4 ms**）。原因是 `enterprise_id = 0` 会匹配所有个人用户，前导列毫无选择性。
因此**该索引已从附录 A 中降级为可选**（仅在企业维度确有选择性时才值得建），并把 `idx_status_date` 列为该查询的主用索引。

> 实测脚本与数据集可复现：`lease_perf` 库 + 本文附录 A 的 DDL。

## 3. 参考实现解析（gf-eshop）

Go 项目有三套缓存实现，构成本项目的直接参照。以下只讲**可迁移的机制**与**必须规避的坑**。

### 3.1 `brands/cache.go` —— ZSET 列表缓存 + Lua 单次往返

这是用户指定的参考文件，核心是三层技巧：

**① ZSET 当有序索引，score 编码复合排序键**

```go
brandScoreScale = 1_000_000_000_000
func encodeBrandScore(sortOrder int, id int64) float64 {
    return float64(int64(sortOrder)*brandScoreScale + (brandScoreScale - id))
}
```

把 `(sort_order ASC, id DESC)` 的复合排序压进一个 float64 score，于是"按业务排序分页"退化成 `ZRANGE`，**不再需要 DB 的 ORDER BY + filesort**。这正是 §2.1.1 中 `/public/products`、`/public/categories` 最需要的技巧。

**② Lua 脚本把 4 次往返压成 1 次**

```lua
local total = redis.call('ZCARD', zkey)          -- 分页总数
local ids   = redis.call('ZRANGE', zkey, start, stop)
-- 先 EXISTS 校验完整性，避免部分 MGET miss
if redis.call('EXISTS', unpack(keys)) < #ids then return {-1} end
local vals  = redis.call('MGET', unpack(keys))   -- 批量取实体
```

关键设计：**用 `EXISTS` 做完整性哨兵**。任何一个实体 key 缺失就返回 `-1`，上层据此触发重建 —— 这解决了"ZSET 还在、实体 key 已过期"导致的**部分 miss 脏读**问题。这个哨兵模式值得照搬。

**③ Mutex + channel 实现 singleflight 防击穿**

```go
rebuildMu.Lock()
ch, ok := rebuilding["brands"]
if !ok || ch == nil {
    ch = make(chan struct{})
    rebuilding["brands"] = ch
    rebuildMu.Unlock()
    _, _ = rebuildBrandCache(context.Background())   // 只有第一个 goroutine 重建
    rebuildMu.Lock(); delete(rebuilding, "brands"); rebuildMu.Unlock()
    close(ch)
    return
}
rebuildMu.Unlock()
<-ch                                                 // 其余 goroutine 等待
```

细节缺陷：`rebuildBrandCache` 用 `context.Background()` 而非传入的 `ctx`（`cache.go:117`）—— 避免了调用方取消导致重建半途而废，但也意味着**重建无法超时中断**。Java 版本建议保留语义但加锁超时。

### 3.2 `products/cache.go` —— L1 + Bloom + L2 三级读

```
L1 本地 map (8192 条, TTL 60s ±20% jitter, RWMutex)
  ↓ miss
Bloom Filter (N=100000, P=0.01, bits-and-blooms/bloom v3)
  ↓ maybe
L2 Redis (SETEX product:{id}, TTL 10min)
  ↓ miss
DB → 回填 L1 + Bloom + L2
```

读路径实现在 `repo_products.go:39-67`，干净的 4 级 fallback：

```go
func getByIDCached(ctx context.Context, id int64) (*entity.Products, error) {
    if p, ok := productLocalCache.get(id); ok { return p, nil }        // 1. L1
    if !productBloom.mayExist(id) { return nil, errcode.ErrProductNotFound } // 2. Bloom 拦截
    if p, err := getProductEntityCache(ctx, id); err == nil && p != nil {    // 3. L2
        productLocalCache.set(p.Id, p); return p, nil
    }
    p, err := getByID(ctx, id)                                          // 4. DB 兜底
    if p == nil { return nil, errcode.ErrProductNotFound }
    _ = setProductEntityCache(context.Background(), p)                  // 回填全部层级
    return p, nil
}
```

三个精巧设计：

**① Bloom 未预热时放行**

```go
func (b *spuBloomFilter) mayExist(id int64) bool {
    c := b.count
    if c == 0 { return true }   // 未预热 → 放行，避免启动瞬间全量 404
    return b.filter.TestString(strconv.FormatInt(id, 10))
}
```

`count == 0` 是"我还没预热好"的信号，此时必须**放行**而非拦截，否则启动后到预热完成之间的请求会被错误判为不存在。这个边界极容易漏掉。

**② TTL 抖动防雪崩**

```go
func jitteredTTL(base time.Duration, jitter float64) time.Duration {
    delta := time.Duration(float64(base) * jitter)
    return base + time.Duration(rand.Int63n(int64(delta*2+1))) - delta
}
```

L1 的 60s TTL 变成 48~72s 随机值。**多级缓存必须有的机制**——否则同批 key 会在同一秒集体失效，瞬间把全部流量打到 L2/DB。

**③ 写路径同时更新三级**

```go
func setProductEntityCache(ctx context.Context, p *entity.Products) error {
    productBloom.add(p.Id)          // Bloom 只增不删
    productLocalCache.set(p.Id, p)  // L1
    g.Redis().Do(ctx, "SETEX", ...) // L2
}
```

### 3.3 必须规避的两个坑

| 坑 | 位置 | 说明 |
|---|---|---|
| **`KEYS` 扫描** | `products/cache.go:338` `g.Redis().Do(ctx, "KEYS", "product:list:ids:*")` | `KEYS` 是 O(N) 且阻塞 Redis 单线程。生产必须换 `SCAN`，或改用版本号 / `SET` 维护 key 清单 |
| **L1 多实例不一致** | `products/cache.go` 的 `productLocalCache` 是进程内 map | 实例 A 更新商品，实例 B 的 L1 最长 60s 才过期。Go 项目单实例下无问题，**Java 侧多副本部署必须靠 Pub/Sub 广播失效或接受 60s 窗口** |

### 3.4 机制映射：Go → Java

| Go 机制 | 文件:行 | Java / Spring 对应 |
|---|---|---|
| `sync.RWMutex` + `map` L1 | `products/cache.go:42-113` | **Caffeine** `Cache<Long, Entity>`（size + expireAfterWrite；抖动需手写） |

## 4. 接口分级：缓存适用性矩阵

分级标准：
- **S** = 公开只读 + 写极少 + 整表小或排序确定 → **L1 + L2 + ZSET 列表缓存**，收益最高、风险最低
- **A** = 读多写少（含计费规则类参照数据）→ **L1 + L2**，写时精准失效
- **B** = 聚合/统计类 → **短 TTL 缓存**（30~60s）
- **C** = 个人流水 / 隐藏写操作 → **不缓存**（先修架构）
- **❌** = 强一致写接口 → **必须直连 DB**

### S 级：公开只读接口（8 个，全部推荐）

| 接口 | 服务方法 | 数据量 | 建议方案 |
|---|---|---|---|
| `GET /public/categories` | `PrdCategoryService.publicList():81` | 4 行 | L1 整表（TTL 10min）+ L2 单 key；写时删 key |
| `GET /public/products` | `PrdProductService.publicPage():127` | 27 行 | **照搬 brands 方案**：ZSET 存 ID（score 编码 `sort_order,id`）+ 实体 key + Lua 分页 |
| `GET /public/products/{id}` | `PrdProductService.publicGet():141` | — | **L1 + Bloom + L2**（全项目唯一真正需要布隆的接口，见 §5） |
| `GET /public/menus?date=` | `PrdDailyMenuService.publicList():127` | 92 行 | key 带日期 `menu:{date}`，TTL 到当日 24:00；L1 + L2 |
| `GET /public/rooms` | `RoomService.publicList():27` | 8 行 | L1 整表 |
| `GET /public/coupons` | `MktCouponService.publicList():88` | 3 行 | L1 整表 |
| `GET /public/recharge-tiers` | `RechargeTierService.publicList():29` | 6 行 | L1 整表 |

## 5. 布隆过滤器的适用范围（严格界定）

### 5.1 判断标准

布隆过滤器只在**同时满足**以下 4 条时产生正收益：

1. 查询**按主键/唯一 ID** 做点查（能表达成集合成员判定）
2. ID 空间**稀疏**：存在大量"一定不存在"的 ID 被查询
3. 存在**绕过缓存的探测流量**（恶意扫描 ID、爬虫、前端 bug 循环）
4. 表足够大，"不存在"的 DB 查询有真实成本

### 5.2 本项目逐接口判定

| 接口 | ①按 ID | ②空间稀疏 | ③有探测流量 | ④表够大 | 判定 |
|---|---|---|---|---|---|
| `GET /public/products/{id}` | ✅ | ✅ 雪花 ID 空间极大 | ✅ 匿名接口，可被 ID 枚举 | ✅ | **上布隆** |
| `GET /products/{id}`（管理端） | ✅ | ✅ | ⚠️ 需管理员 token | ✅ | **上布隆**（复用同一 filter） |
| `GET /public/rooms`（整表） | ❌ 列表 | — | — | ❌ 8 行 | ❌ 用整表 L1 |
| `GET /rooms/{id}` | ✅ | ❌ id 连续小整数 | ❌ | ❌ 8 行 | ❌ 无收益 |
| `GET /public/categories` / `{id}` | ❌ | ❌ | ❌ | ❌ 4 行 | ❌ 整表 L1 |
| `GET /public/menus` / `{id}` | ❌ | ❌ | ❌ | ❌ 92 行 | ❌ 整表 L1 |
| `GET /public/coupons` / `{id}` | ❌ | ❌ | ❌ | ❌ 3 行 | ❌ 整表 L1 |
| `GET /public/recharge-tiers` | ❌ | ❌ | ❌ | ❌ 6 行 | ❌ 整表 L1 |
| `GET /public/member-levels` | ❌ | ❌ | ❌ | ❌ 3 行 | ❌ 整表 L1 |
| `GET /me/orders/{id}` | ✅ | ✅ | ⚠️ | ✅ | ⚠️ 可选。归属校验在加载之后，布隆只能省"ID 完全不存在"的分支，收益有限且需处理租户隔离，**建议先不做** |

**结论：全项目布隆过滤器的唯一明确目标是「商品详情」这一条链路。**

### 5.3 一个对本项目特别有利的性质：ID 只增不复用 + 逻辑删除

这是**关键的正确性论证**：

- `prd_products` 主键是 MyBatis-Plus 雪花 ID（`id-type: assign_id`），**永不复用**
- `prd_products` 启用逻辑删除（`is_deleted`），`deleteById` 实为 `UPDATE ... SET is_deleted=1`，**行永远物理存在**

因此：

> **布隆过滤器只增不删，永远不产生假阴性。** 已删除/下架的商品，布隆会说"可能存在" → 落到 DB → 业务层判 404。丢掉的只是一次优化，**不会出错**。

这点至关重要：布隆过滤器**标准实现不支持删除元素**（无法安全清零 bit）。若本项目是物理删除 + ID 复用，布隆就会产生假阴性 → **把存在的商品误判为不存在 → 用户看到 404 而数据其实在**。这里恰好规避。

**但下架/删除后的 404 会被反复打 DB**，必须配套 **短 TTL 空值缓存**：

```
product:null:{id}  →  SETEX 60s
```

| 机制 | 拦截的流量 | 是否可删 |
|---|---|---|
| 布隆过滤器 | **从来没存在过**的 ID（随机扫描） | 只增不删，安全 |
| 空值缓存（60s） | **存在但当前不可见**（已下架/已逻辑删除） | 可删，到期自动重查 |

### 5.4 ⚠️ 多实例部署下的假阴性风险（必读）

布隆过滤器**在每个 JVM 进程内各一份**。多副本部署时：

```
时刻 T：请求打到实例 A → 管理员新建商品 id=999
       实例 A 的 bloom.add(999) ✅
       实例 B 的 bloom 里没有 999 ❌
时刻 T+1：用户请求打到实例 B → GET /public/products/999
       实例 B 的 bloom.mayExist(999) == false
       → 直接返回 404，但商品是存在的！  ← 严重 BUG
```

这是把 Go 单实例方案直接搬到 Java 多副本时**最容易踩的坑**。三种解法：

| 方案 | 做法 | 评价 |
|---|---|---|
| ① 定时补齐（推荐） | 每 30s 执行 `SELECT id FROM prd_products WHERE id > :lastMaxId` 增量 add | 实现最简单，窗口 ≤ 30s，可接受 |
| ② Redis Pub/Sub 广播 | 写路径 `PUBLISH product:new {id}`，各实例订阅后 `bloom.add(id)` | 窗口毫秒级，但引入消息通道依赖 |
| ③ Redis 共享布隆 | RedisBloom 模块（`BF.ADD` / `BF.EXISTS`） | 强一致，但多一次网络往返，**与"拦截 DB 查询"的初衷相悖** |

**建议 ①+② 组合**：定时补齐兜底 + Pub/Sub 加速。并明确记录：窗口期内的新建商品在其它实例上可能返回 404。

> 当前 `docker-compose.yml` 是单实例部署，此风险暂不触发；但方案要按多副本设计，否则扩容即故障。

### 6.3 核心骨架（对照 Go 实现逐条映射）

**① 多级读门面 —— 对应 `repo_products.go:39-67`**

```java
public <T> T getOrLoad(String key, Class<T> type,
                       Duration l1Ttl, Duration l2Ttl, Supplier<T> loader) {
    // 1. L1（Caffeine，内建 per-key 互斥，等价 Go 的 singleflight）
    T hit = l1.getIfPresent(key);
    if (hit != null) return hit;

    // 2. L2 Redis
    String json = redis.opsForValue().get(key);
    if (json != null) {
        T v = deserialize(json, type);
        l1.put(key, v);                       // 回填 L1
        return v;
    }

    // 3. DB 兜底（Caffeine.get(key, fn) 保证同 key 只有一个线程穿透）
    return l1.get(key, k -> {
        T loaded = loader.get();
        if (loaded != null) {
            redis.opsForValue().set(key, serialize(loaded), jitter(l2Ttl)); // TTL 抖动
        }
        return loaded;                        // null 需用空值哨兵包装，防穿透
    });
}

/** 对应 Go 的 jitteredTTL —— 防雪崩，必须加 */
private static Duration jitter(Duration base) {
    long ms = base.toMillis();
    long delta = (long) (ms * 0.2);
    return Duration.ofMillis(ms + ThreadLocalRandom.current().nextLong(-delta, delta + 1));
}
```

**② 布隆过滤器 —— 对应 `products/cache.go:117-156`**

```java
@Component
public class BloomFilterRegistry {
    private static final int    N = 100_000;
    private static final double P = 0.01;

    private final BloomFilter<Long> productBloom =
            BloomFilter.create(Funnels.longFunnel(), N, P);
    private volatile boolean ready = false;   // 对应 Go 的 count == 0
    private final ReadWriteLock lock = new ReentrantReadWriteLock();

    /** 对应 mayExist：未预热必须放行，否则启动瞬间全量 404 */
    public boolean mayExist(long id) {
        if (!ready) return true;
        lock.readLock().lock();
        try { return productBloom.mightContain(id); }
        finally { lock.readLock().unlock(); }
    }

    public void add(long id) {
        lock.writeLock().lock();
        try { productBloom.put(id); }
        finally { lock.writeLock().unlock(); }
    }

    public void markReady() { this.ready = true; }
}
```

> ⚠️ Guava `BloomFilter` **非线程安全**，必须自加读写锁。Go 的 `bits-and-blooms/bloom` 同样非并发安全，参考实现已用 `sync.RWMutex` 包住（`products/cache.go:118`）—— 这点要照抄。

**③ ZSET 列表缓存 —— 对应 `brands/cache.go`**

`brands/cache.go` 的 Lua **可原样复用**，只需把 key 前缀从 `brand:` 换成 `product:`，`EXISTS` 完整性哨兵返回 `-1` 的约定照搬：

```java
private static final RedisScript<List> PRODUCT_PAGE_SCRIPT =
        RedisScript.of(PRODUCT_LIST_LUA, List.class);

List<Object> raw = redis.execute(PRODUCT_PAGE_SCRIPT,
        List.of("product:ids:" + suffix),

```

排序 score 编码同理：

```java
static double encodeScore(int sortOrder, long id) {
```

## 7. 风险与陷阱清单

| # | 陷阱 | 说明 | 规避 |
|---|---|---|---|
| 1 | **布隆假阴性 = 数据不可见级 BUG** | 多实例下新建商品在其它实例被误判 404（§5.4） | 定时增量补齐 + Pub/Sub |
| 2 | **布隆不支持删除** | 已下架商品仍被判"可能存在" | 配套 60s 空值缓存（§5.3） |
| 3 | **未预热放行** | `ready=false` 时必须放行，否则启动瞬间全量 404 | 照搬 Go 的 `count == 0 → return true` |
| 4 | **TTL 雪崩** | 同批 key 同时失效打穿到 DB | 强制 TTL 抖动 ±20% |
| 5 | **缓存与事务不一致** | 事务提交前写缓存 → 回滚后脏数据 | `afterCommit` 才写缓存/发失效 |
| 6 | **`KEYS` 命令** | 参考实现 `products/cache.go:338` 用了 `KEYS`，生产会阻塞 Redis | 用 `SCAN` 或版本号方案 |
| 7 | **缓存穿透** | 不存在的 ID 每次打 DB | 布隆 + 空值缓存双保险 |
| 8 | **缓存击穿** | 热点 key 失效瞬间并发打 DB | Caffeine `get(key, fn)` 或 Redis 分布式锁 |
| 9 | **`OR` 条件破坏索引** | `publicPage` 的 `(product_status IS NULL OR product_status = 2)` | 改 `UNION ALL` 或规范化 NULL，否则加索引无效 |
| 10 | **逻辑删除与索引** | 6 张表自动追加 `is_deleted=0`，索引未覆盖 | 复合索引末位加 `is_deleted` |
| 11 | **Jackson 3** | 本项目用 `tools.jackson.databind.ObjectMapper`（Jackson 3），非 `com.fasterxml` | 序列化统一走已注入的 Bean，勿新建 |
| 12 | **GET 内含写操作** | 会议预约两个列表接口含过期清理（§2.0） | **先移到定时任务，再谈缓存**，否则缓存会掩盖故障 |
| 13 | **schema 双轨漂移** | Flyway 与 `db/*.sql` 已不一致（§2.1.3） | 补 `V11__add_indexes.sql` 并回归比对两条轨道 |

## 8. 优先级总结（按投入产出比排序）

| 排名 | 事项 | 类型 | 理由 |
|---|---|---|---|
| 1 | `expirePastReservations` 移出 GET 改为定时任务 | 架构 | GET 写库 + 无界 + N+1，最坏 `3E+3Ep` 条 SQL 且无事务 |

| 4 | 3 张计费规则表 + 8 个公开接口上 L1 | 缓存 | 一次配置消掉大量重复查询 |
| 5 | 修 `enterprise_id=0` 的统计口径 | 正确性 | 既是性能问题也是逻辑错误 |
| 6 | `/public/products` 上 L1 + L2 + ZSET | 缓存 | 最热的公开接口 |
| 7 | 商品详情上布隆 + 空值缓存 | 缓存 | 唯一的布隆有效场景 |
| 8 | 补 `@Transactional`、消除重复查询、修 schema 漂移 | 健壮性 | 消除 TOCTOU 与 500 误报 |

> **一句话总结**：本项目 Redis 已就位但业务零使用，读路径全部直连 MySQL；然而**当务之急不是加缓存，而是先修索引、无界查询、以及 GET 里的写操作**——缓存应该建在已经正确的查询之上。布隆过滤器全线只有「商品详情」一个接口值得上，且必须配套空值缓存与多实例增量补齐，否则会把"防穿透"做成"误 404"。

```sql
SELECT table_name, index_name, GROUP_CONCAT(column_name ORDER BY seq_in_index)
FROM information_schema.statistics
WHERE table_schema = 'lease_db'
GROUP BY table_name, index_name
ORDER BY table_name, index_name;
```
